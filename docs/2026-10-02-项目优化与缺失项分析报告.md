## 一、先说结论

项目工程化程度比文档描述的更成熟：**577 个单元测试全绿、`pnpm build` 通过、ESLint 零告警**，面试模块的并发控制（乐观锁、幂等清扫、归属校验）做得相当扎实，OAuth 令牌落库加密、Token 黑名单 TTL 等细节也到位。

真正的问题集中在三类，且都是**「测试网覆盖不到的地方」**：

1. **部署链路是断的**——构建产物落在 `dist/src/main.js`，而所有启动命令都指向 `dist/main`，三条部署路径启动即崩。
2. **权限体系只有一半**——`/admin/**` 共 10 个接口只校验「登录」，任何注册用户都能读取和物理删除他人的简历；`GET /user` 甚至把所有用户的 OAuth 令牌一并返回。
3. **文档承诺的能力实际不存在**——限流、e2e、类型检查、角色校验，文档都写了，代码里都没挂上。

## 三、P0：上线阻断级

### P0-1 构建产物路径错误，三条部署路径全部启动失败

**证据（我实测）**
- `pnpm build` 成功后：`Test-Path dist/main.js` → **False**；`Test-Path dist/src/main.js` → **True**；`dist/` 下只有 `src/`、`scripts/`。
- 启动命令却全部指向 `dist/main`：`package.json` `"start:prod": "node dist/main"`、`Dockerfile:62` `CMD ["node", "dist/main"]`、`ecosystem.config.js:17` `script: './dist/main.js'`、`railway.json` `startCommand: "npm run start:prod"`。

**根因**：`tsconfig.build.json` 只写了 `exclude`，没有限制 `include`。`scripts/**/*.ts` 也被纳入编译，公共根目录因此上抬到项目根，产物变成 `dist/src/main.js` + `dist/scripts/*.js`。

**影响**：`pnpm start:prod`、Docker `CMD`、PM2、Railway 四条路径全部 `MODULE_NOT_FOUND`；容器健康检查失败并循环重启。

**修复**：`tsconfig.build.json` 增加 `"include": ["src/**/*.ts"]`（推荐），或把四处启动命令统一改为 `node dist/src/main`。修完必须用 `docker compose up --build` 或 `pnpm build && pnpm start:prod` 实测一次。

### P0-2 `/admin/**` 系列接口无角色校验：任意登录用户可读删他人数据

**证据**
- `src/resume/admin-resume.controller.ts:20-21`：`@Controller('admin/resumes')` + `@UseGuards(JwtAuthGuard)`，注释自认 `TODO: 当角色系统完善后添加 AdminGuard`；`GET /admin/resumes`（跨用户分页）、`GET /admin/resumes/:id`（`resume.service.ts:764` 用 `findById`，无 userId 过滤）、`DELETE /admin/resumes/:id`（`resume.service.ts:777` `findByIdAndDelete` + 级联删除 AI 记录）。
- 同样形态：`src/admin/admin.controller.ts:12`（仪表盘）、`src/user/admin-users.controller.ts:12`（用户统计）、`src/resume-ai/ai-usage-record.controller.ts:18`（用量记录列表/详情/**删除**）。
- **角色体系根本不存在**：`src/auth/strategies/jwt.strategy.ts:32-36` 只回填 `userId/username/email`；`src/user/user.service.ts:141-145` 签发 token 时不带 `role`；`src/user/entities/user.entity.ts` **没有 role 字段**；`src/app.module.ts:62-76` 只有 `APP_FILTER` + 两个 `APP_INTERCEPTOR`，**没有 `APP_GUARD`**。
- 因此 `src/user/user.controller.ts:121/139/187` 的 `req.user.role === 'admin'` **恒为 false**——按 TODO 直接加 `AdminGuard` 也会失效，必须先补 role 数据链路。

**影响**：任意注册用户（注册接口 `POST /user` 无守卫、无邮箱验证）拿到自己的 token 后，即可分页枚举全站简历、读取他人完整简历（含姓名/手机/邮箱）、**物理删除他人简历并级联清空其 AI 记录**；删除日志只写「管理员删除简历 {id}」，无法追责。

**修复**（按顺序）
1. `User` schema 增加 `role` 字段；签发 token 与 `JwtStrategy.validate` 回填 `role`。
2. 新增 `AdminGuard`（或 `@Roles('admin')` + `RolesGuard`），替换 4 个 admin 控制器上的 `JwtAuthGuard`。
3. 在 AdminGuard 就绪前，先在 nginx 层对 `/api/v1/admin/` 返回 403 止血。
4. 补一条带全局管道的 supertest e2e：普通用户访问 `/admin/resumes*` 必须 403。

### P0-3 `GET /user` 对任意登录用户开放，并泄露全站用户的 OAuth 令牌

**证据**
- `src/user/user.controller.ts:72-76`：`@UseGuards(JwtAuthGuard) @Get()` → `userService.findAll(query)`，**没有任何管理员判断**（旁边就是 `// TODO: 当角色系统完善后添加 AdminGuard`）。
- `src/user/user.service.ts:229-231`：`.find(filter).select('-password')` —— **只排除了 password**；而 `accessToken/refreshToken` 在 `src/user/entities/user.entity.ts:44-58` 未声明 `select: false`，schema 也没有 `toJSON` 脱敏。
- `GET /user/:id`（`user.controller.ts:183`）同样返回整份文档。

**影响**：任意登录用户可分页拉取全部用户的用户名、邮箱、注册来源、登录失败次数、第三方平台 ID/昵称/头像，以及 **OAuth accessToken / refreshToken**。令牌在配置了 `ENCRYPTION_KEY` 时为密文（`src/common/oauth/base-oauth.service.ts:190-191`），未配置时（`src/common/crypto.module.ts:13` 明确允许）为**明文**；即便是密文，凭据外泄也不可接受。

**修复**：`findAll/findOne` 改为白名单 `select`（如 `username email createdVia createdAt`），或在 `UserSchema` 加 `toJSON` transform 剥离 `oauthProviders`；同时补上管理员鉴权。

### P0-4 限流从未生效：`ThrottlerGuard` 未注册

**证据（我实测）**
- `src/app.module.ts:31` 注册了 `ThrottlerModule.forRoot([{ ttl: 60000, limit: 30 }])`，但同文件 `providers`（62-76 行）只有 `APP_FILTER` 与两个 `APP_INTERCEPTOR`，**没有 `APP_GUARD`**。
- `grep -r "ThrottlerGuard|APP_GUARD|useGlobalGuards" src` → **0 命中**；`git log -S "ThrottlerGuard"` 无输出（从未生效过）。
- 控制器上共 6 处 `@Throttle({ default: { limit: 10, ttl: 60000 } })`（`user.controller.ts:50` 登录、三个 OAuth 回调、`interview.controller.ts:30`、`resume-ai.controller.ts:40`）——**全是死代码**。
- 文档却宣称生效：`AGENTS.md`「Global rate limiting: 30 requests / 60 s」、`docs/api/mock-interview.md:12`「每 IP 每 60 秒最多 10 次」。

**影响**：登录接口仅剩「同账号 5 次失败锁 30 分钟」兜底，跨账号喷洒不受限；AI 生成、SSE 答题、PDF 导出等付费/昂贵端点可被无限调用。**唯一实际限流来自可选的 nginx**（`nginx.conf:1` `rate=10r/s`），而 `DEPLOYMENT.md:210` 把 nginx 标为「可选」，Railway（NIXPACKS）路径完全无限流。

**修复**：在 `AppModule` providers 注册 `{ provide: APP_GUARD, useClass: ThrottlerGuard }`；对 AI/PDF 端点用 `getTracker` 改为按 `userId` 计数并单独收紧；补一条 e2e（连打 11 次断言 429），否则该回归无法被单测发现。

### P0-5 登录逻辑可被用于锁定任意账号，并泄露账号是否存在

**证据（`src/user/user.service.ts:80-131`）**
- 锁定检查在**密码校验之前**（`:90` 判断 `lockedUntil` 后直接抛错），且失败计数是**账号维度**、与来源 IP 无关 → 攻击者只需知道邮箱，连发 5 次错误密码即可把该用户锁 30 分钟（`:116-122`）。
- 错误文案可区分账号状态：`:105-107`「该账户通过第三方平台注册」、`:97-99`「账户已被锁定,请 X 分钟后再试」、`:86`「用户不存在或密码错误」——**账号枚举**。
- 注释与实现漂移：`:46-49` 注释写「60 秒内最多 5 次」，实际装饰器是 `limit: 10`（`user.controller.ts:50`），且该装饰器因 P0-4 完全无效。

**修复**：失败计数按「账号 + IP」双维度并在比对密码之后再决定是否锁定；统一错误文案为「邮箱或密码错误」；OAuth 注册提示改为通过邮件/前端引导而非响应体区分；恢复限流后把登录限制定为 5-10 次/分钟并加指数退避。

### P0-6 上传扩展名可伪造，构成同源存储型 XSS

**证据**
- `src/common/upload/upload.module.ts:42-53`：`fileFilter` **只校验客户端提交的 `file.mimetype`**（可任意伪造），`:35-40` 存储文件名取 `extname(file.originalname)`，**不校验扩展名与内容特征**。
- `src/common/upload/upload.controller.ts:19-28`：`POST /upload/image` 返回 `/uploads/<filename>`；`src/main.ts:77-79` 把 `uploads/` 挂为**公开静态目录**（无鉴权）。
- `src/main.ts:58-68` 的 CSP 只显式设置了 `defaultSrc 'self'` 与 `imgSrc`，`scriptSrc` 回落到 `'self'` → **同源脚本可执行**。

**影响**：攻击者上传 `evil.html`（multipart 里把 `Content-Type` 写成 `image/png`），文件以 `.html` 落盘并通过 `/uploads/evil.html` 公开访问，在 API 同源下执行任意 JS（可读取同源 `localStorage` 中的 JWT）。

**修复**：白名单映射「MIME ↔ 扩展名」并强制按 MIME 推导落盘扩展名；用 `file-type` 之类读魔数二次校验；对图片做重编码；给 `/uploads/` 加 `Content-Disposition: attachment` 或独立域名，并把 CSP 的 `scriptSrc` 明确收紧。

## 四、P1：高价值优化项

### P1-1 AI 调用超时与重试策略叠加，最坏 21 次上游调用

- `src/ai/ai.service.ts:43-50` 创建 `ChatDeepSeek` 时**既不设 `timeout` 也不设 `maxRetries`**：LangChain `AsyncCaller` 默认 `maxRetries = 6`，而业务层 `src/ai/chain-invoke.utils.ts:8` 的 `AI_INVOKE_RETRIES = 2` 又叠了一层 → 单次逻辑调用最坏 `(1+2)×(1+6) = 21` 次上游请求，且外层重试之间**没有退避**（`chain-invoke.utils.ts:95-127`）。
- 两个调用点**完全没有超时**：`src/resume-ai/resume-ai.service.ts:464-486`（`createResumeByAi`）与 `:689-733`（`parseResume`），只重试不设 timeout/signal；OpenAI SDK 默认超时 10 分钟。
- 两处裸 `Promise.race` 超时后**不中止上游**：`resume-ai.service.ts:1418-1430`、`:1727-1742`（无 `signal`、定时器未 `clearTimeout`），超时后请求仍在跑（仍计费）。对比正确写法在 `src/ai/chain-invoke.utils.ts:106-126`。
- 项目自己已按最坏值留窗口：`src/interview/constants/level.constants.ts:158-163` 注释「120s ×(2+1)=6 分钟，取 8 分钟留缓冲」。

**修复**：工厂层钉死 `maxRetries: 0/1` 与 `timeout`；业务层统一走 `invokeChainWithRetry` 并加带抖动的指数退避；只对网络/5xx/429 重试，4xx 立即失败；把「构造参数（timeout/maxRetries）」写进 `ai.service.spec.ts` 作为回归基线。

### P1-2 SSE 断连检测失效：客户端离开后仍在跑完并计费（我实测）

**我做的验证**：用 Node 原生 http 复刻 `pipeSse` 的注册时机（先 `await` 业务、300ms 后才注册监听），客户端在 118ms 断开：

```
handler-start 19ms        REQ-CLOSE fired 20ms   ← 请求体读完就触发（Node ≥16 语义）
body-consumed 20ms req.complete=true
client-destroy 116ms      RES-CLOSE fired 117ms  ← 真正代表客户端断开
after-await 335ms  req.destroyed=true            ← 此时才注册监听 ⇒ 上面两个事件都已错过
```

结论：`src/interview/interview.controller.ts:282` 的 `req.on('close')` 在 `:131 await` 之后注册，**永远不会触发**（第一版探针里断连后该监听器一次都没执行）。而 `res.on('close')` 才是可靠信号。

**影响**：`docs/api/mock-interview.md:381` 承诺的「客户端断开会自动取消订阅」不成立——用户离开后出题/报告（最坏 480s）继续跑完并计费。

**修复**：`pipeSse` 改用 `res.on('close')` 取消订阅（保留 `req.on('error')` 兜底），并补一条断言「断连即 unsubscribe」的测试。

### P1-3 SSE 无心跳，与仓库自带 nginx 读超时冲突

- `src/interview/interview.controller.ts` 两个流式端点**没有心跳**；`src/common/sse.utils.ts:17` 只在事件到达时写帧。
- 报告生成静默时长：`src/interview/services/evaluation.service.ts:21-23` `REPORT_TIMEOUT_MS = 240_000` + `REPORT_RETRIES = 1` → 最长 **480s 静默**；出题链 `120s × 3 = 360s`。
- 但仓库自己的 `nginx.conf:13` 是 `proxy_read_timeout 120s`（`docker-compose.yml` 默认挂载它）→ 最贵的报告阶段最易被 504 掐断。
- 对照：`src/resume-ai/resume-ai.service.ts:1074` **有** `interval: 30000` 心跳，可照搬。

### P1-4 面试模块无成本上限、零用量记账

### P1-13 OAuth 按邮箱自动绑定，且不验证邮箱归属 → 可预注册他人邮箱实现账号接管

**证据（我读码确认）**

## 五、P2：可维护性与质量保障

### P2-1 测试体系的三个结构性缺口
1. **spec 的类型错误永远不被检查**（我实测）：`tsconfig.json:7` `isolatedModules: true` → ts-jest 走 transpile-only（`ts-jest/dist/legacy/compiler/ts-compiler.js:74` 的 `if (!this.configSet.isolatedModules)` 分支被跳过）；`tsconfig.build.json` 又 `exclude: ["**/*spec.ts"]`。于是 `npx tsc --noEmit` 报的 **13 个错误全部躺在 spec 里**（`interview-session.entity.spec.ts`、`resume-records.mapper.spec.ts`、`ai.controller.spec.ts`），而 `pnpm test` 依然全绿——**假绿**。
2. **e2e 实际不存在**：`test/jest-e2e.json` 缺 `moduleNameMapper`，`pnpm test:e2e` 直接 `Cannot find module 'src/auth/guards/jwt-auth.guard'`；而且唯一的 `test/app.e2e-spec.ts` 是 Nest 脚手架残留（断言 `GET /` 返回 `Hello World!`），既不经过全局前缀也不经过 ValidationPipe/Guard/Filter。
3. **关键面零覆盖**：165 个非 spec 源文件中只有约 35 个有同名 spec；`src/auth`（5 文件）、`src/common/filters`（3）、`src/common/oauth`（4）、`src/common/utils`（5）、`src/common/upload`（3）、三个 OAuth 模块（各 4）、`src/template`（7）**全都没有 spec**；`UserService` 15 个公开方法只测了 3 个，`login/logout/changePassword/remove` 这类写操作全无断言；所有 spec 里「Guard」关键词命中数为 0——**删掉任意 `@UseGuards(JwtAuthGuard)` 都不会被测试发现**。

**建议**：① 加 `typecheck: tsc --noEmit` 脚本并修掉 13 个错误；② 修 `jest-e2e.json` 的 `moduleNameMapper`，把脚手架换成真实业务 e2e（注册 → 登录 → 鉴权 → 一次 CRUD → 一次越权断言 403）；③ 优先补 `jwt.strategy`、`token-blacklist.service`、`sanitize-user.util`、`base-oauth.service` 四个 spec。

### P2-2 质量门禁缺失
无 `.github/workflows`、无 `.husky`、无 lint-staged、`package.json` 无 `coverageThreshold`、无 `typecheck` 脚本。这直接解释了为什么 13 个 spec 类型错误、130 个未测源文件可以长期存在。建议加一条 GitHub Actions（lint + typecheck + test:cov）与 statements/lines 60% 起步的覆盖率阈值。

### P2-3 可观测性基本空白
`grep` 在 `src` 中 **0 命中**：Swagger/OpenAPI、metrics、OpenTelemetry、Sentry。唯一健康检查 `src/app.controller.ts:18-33` 只读 Mongo `readyState`，且 `status: 'degraded'` 时**仍返回 HTTP 200** → Mongo 断连时 Docker/Railway 仍判健康，不会摘流量。日志侧：`src/common/logger/winston.config.ts:86` 直接读 `process.env.LOG_LEVEL`（**违反「只用 ConfigService」的硬约束**）；异常过滤器会把非 `HttpException` 的 `error.message` 原样返回客户端（`src/common/filters/all-exceptions.filter.ts:38-39,55`），存在内部错误信息外泄。建议接 `@nestjs/terminus`（不健康返回 503）、`@nestjs/swagger`、prom-client/OTel，并给 mongoose 加 >100ms 慢查询日志。

## 八、已核实「无需改动」的部分（避免误伤）

为避免把力气花在没问题的地方，以下是经对抗复核或我亲自读码确认**健壮**的部分：

- **面试模块的归属校验是完整且一致的**：所有会话读写都经 `findOwnedSession` / `requireActiveSession` 过滤 `userId`（`interview.service.ts:118-140, 233-235, 288-290, 868-871, 1197-1204` 等），未发现 IDOR；过期清扫用 `updateMany` + `status` 前置条件，天然幂等，不会误删活跃会话；会话轮次用条件更新挡并发（spec 里有并发 409 用例）。
- **Token 黑名单设计正确**：`token-blacklist.entity.ts:14` 有 `expireAfterSeconds` TTL 索引，且按 `tokenHash` 唯一索引查询（`token-blacklist.service.ts:19-21`）；原始 token 入库属可改进项，不是漏洞。
- **OAuth 令牌落库是加密的**：配置 `ENCRYPTION_KEY` 时走 AES-256-GCM（`src/common/oauth/base-oauth.service.ts:190-191`、`src/common/utils/crypto.util.ts:34-44`）；未配置时才降级为明文并打印告警。
- **上传有 MIME 白名单与 10MB 限制**（`upload.module.ts:10-22,54-56`）——问题只在扩展名推导（P0-6）。
- **统一响应拦截器不会破坏 SSE 与 PDF 下载**：两个流式端点与 PDF 下载都用 `@Res()` 直写（`interview.controller.ts:126`、`resume-ai.controller.ts:81,436`、`resume.controller.ts:49`），`ResponseInterceptor` 不介入，实测路径正常。
- **SSE 的错误帧处理是克制的**：`interview.controller.ts:142-143` 只透传 `HttpException.message`，内部错误统一为「服务器内部错误」——比 `AllExceptionsFilter` 的处理更严谨。
- **AI 层已有两处正确的超时实现**可作为模板：`resume-ai.service.ts:1927-1931`（分析）与 `:2194-2198`（押题）使用了 `AbortController`；`chain-invoke.utils.ts:106-126` 有 `signal` + `finally clearTimeout`。
